# 자료구조 계열 — STACK · QUEUE 기획

> 노션 "Compile-or-Die 기획서" 에 붙여넣기용. 2026-09-01 확정.

---

## 설계 원칙

자료구조 증강의 어려움은 **LIFO / FIFO 가 화면에서 안 보인다**는 것이다.
뱀서라이크는 적이 초당 여러 마리 죽고 새로 나오기 때문에, 플레이어가
"누가 먼저 들어갔는지"를 추적할 방법이 없다.

그래서 순서를 **다른 채널로 번역**한다.

| | 순서를 무엇으로 보여주나 |
|---|---|
| STACK | **시간** — 연쇄 폭발의 리듬 |
| QUEUE | **색** — 표식이 진해지는 정도 |

그리고 두 증강이 파는 것은 순서 규칙이 아니라 **사람들이 실제로 아는 개념**이다.
스택은 *스택 오버플로우*, 큐는 *대기열*.

---

## STACK

**분류** 자료구조 · **컨셉** 스택 오버플로우
**한 줄** 준 피해를 좌표째 쌓아두었다가, 넘치면 역순으로 되짚으며 터뜨린다

### 동작

```
[기록]   모든 피해가 파이프라인을 지날 때  { 좌표, 그 피해 } push
         ✘ 자기 폭발은 안 넣음 (무한루프 방지)
         ✘ 대기 중에는 기록하지 않음

[평상시] 1초 고정 간격으로 맨 위 하나 pop → 그 좌표에서 폭발
         딜이 아니라 "작동 중" 신호. 스탯을 받지 않는다

[유예]   경계 초과 후 1초 — 계속 push 를 받는다   ( 130 / 80 )
         경고 이펙트. 이 1초에 더 때릴수록 보상이 커진다

[폭발]   맨 위부터 전부 역순 연쇄
         · 연출 길이 ~2초 고정. 프레임이 많으면 간격을 줄여 밀도로 표현
         · 가짜 렉 — timeScale 순간 하강 + 불규칙 간격 + 글리치 + 오디오 피치
         · 개별 피해 숫자 없음. HUD 에 총합을 실시간 카운트업

[대기]   쿨타임 스탯. 기록도 멈춘다 → 이것이 유일한 비용이자 가동률
```

**폭발 피해 = 기억한 피해 × 비율 + 고정치**

### 수치 축

| 시트 칸 | 의미 | 메모 |
|---|---|---|
| 쿨타임 | 오버플로우 후 대기시간 | ★ 핵심 성장축 |
| 깊이 | 스택 경계 (초기 80) | |
| 효과피해 | 비율 | 5% 미만 |
| 피해량 | 고정치 | 아주 낮게 — 프레임 수에만 비례해 폭주 위험 |
| 효과범위 | 폭발 반경 | |
| 지속시간 | 유예 시간 | 1초 고정으로 시작, 나중에 개방 |

### 성격

- **탐색 의존 없음.** 폭발이 탐색 대상에 닿으면 표식 추가피해 — 시너지는 있되 의존은 없다
- **범용이되 천장이 낮다.** 총 피해의 약 5%. 끝까지 주력이 되지 못한다
- **연쇄 · 트리가 짝.** 프레임 수가 늘어 오버플로우가 잦아진다

### 설계 근거

- **평상시 pop 은 딜이 아니라 신호다.** 5% 짜리 한 방은 기여가 거의 없지만
  스택은 확실히 갉아먹는다. 0.5초로 두면 초반 단일 빌드(초당 1~2히트)에서
  pop 이 push 를 앞질러 **평생 오버플로우를 못 본다.** 1초가 하한.
- **쿨타임 스탯을 대기시간에 붙이는 이유.** 평상시 pop 이 쿨타임을 받으면
  쿨감 → pop 빨라짐 → 스택이 안 참 → 오버플로우 실종, 즉 **쿨감이 증강을 약하게 만든다.**
  대기시간에만 붙이면 쿨감이 순수하게 가동률로 간다.
- **유예 구간은 버퍼 오버런 그 자체다.** 진짜 스택 오버플로우도 경계를 넘는
  즉시 멈추지 않고 넘어서 계속 써 내려가다 터진다. `130/80` 이 그 구간.
- **연출 길이를 프레임 수와 분리하는 이유.** 130 × 0.05 = 6.5초는 늘어진다.
  길이를 고정하고 간격을 줄이면 오버필이 **밀도**로 표현되어 지겹지 않다.

## QUEUE

**분류** 자료구조 · **컨셉** 대기열 / FIFO
**한 줄** 탐색된 적을 줄 세워 순서대로 처리한다. 오래 기다린 적일수록 아프다

### 동작

```
[인큐]   탐색 표식이 붙은 적이 큐에 들어간다
         큐가 가득 차면 들어가지 않는다 — 표식 자체는 그대로 (탐색에 페널티 없음)
         ★ 큐 표식이 따로 붙는다. 탐색 표식과 별개 시각

[대기]   큐에 있는 동안 대기 시간이 쌓인다
         큐 표식이 점점 진해진다 = 내 차례가 가까워진다

[디큐]   간격마다 맨 앞(= 가장 오래 기다린 적)을 처리
         피해 = 기본 피해 + 대기 시간 × 증가율   (상한 있음)
         ★ 디큐 피해를 받아야 탐색 표식이 풀린다

[백프레셔] 큐가 가득 차면 디큐 간격이 짧아진다
           → 대기가 짧아져 개별 피해 감소, 총 처리량은 유지
```

적이 중간에 죽으면 큐에서 빠지고 순서는 유지된다.

### 수치 축

| 시트 칸 | 의미 |
|---|---|
| 수량 | 큐 최대 크기 |
| 쿨타임 | 기본 디큐 간격 |
| 피해량 | 디큐 기본 피해 |
| 효과피해 | 대기 시간당 피해 증가율 |
| 지속시간 | 대기 보너스 상한 |

### 설계 근거

- **"오래 기다린 놈이 더 아프다" 가 FIFO 를 수치로 만드는 유일한 장치다.**
  앞에서 빼든 뒤에서 빼든 결과가 같으면 순서는 장식이다.
- **백프레셔는 리틀의 법칙 그대로다** (`대기열 = 도착률 × 대기시간`).
  적이 몰릴수록 얕게 처리하고, 적을 때 깊게 처리한다.
  → **스택과 정확히 반대**: 스택은 몰릴수록 강해지고 큐는 얕아진다
- **대기 보너스 상한은 필수.** 적이 한 마리만 남아 30초를 기다리면 피해가 폭주한다.
- **숨은 시너지** — 디큐할 때까지 표식이 유지되므로 탐색풀 전체의 유지력이 올라간다.
  `SearchPoolTargeting` 을 쓰는 트리 · 그래프가 대상을 훨씬 잘 찾게 된다.
  즉 큐는 딜러이면서 탐색 계열의 서포트다.

## 두 증강의 대비

| | STACK | QUEUE |
|---|---|---|
| 쌓는 것 | 내가 준 피해 | 적의 대기 시간 |
| 정보 위치 | 내 HUD 게이지 | 적 몸의 표식 |
| 방출 | 한 번에 폭발 | 하나씩 꾸준히 |
| 탐색 | 무관 | **필수** |
| 짝 | 연쇄 · 트리 | 탐색 (BFS · DFS) |
| 적이 몰리면 | **강해짐** (프레임 축적) | **얕아짐** (백프레셔) |
| 성격 | 간헐적 대량 | 꾸준한 소량 |

모든 줄이 반대다. 같은 계열인데 겹치는 것이 없다.

---

## 풀 관리 (별건, 선행 필요)

큐 · 그래프처럼 탐색이 없으면 아무것도 못 하는 증강이 늘면
**레벨업 3택에 죽은 카드가 섞인다.**

현재 `AugmentDraft.CanAppear` 의 선행 조건은 `rootAugment` 하나뿐이고
이것은 **특정 증강 1개**를 가리킨다. "탐색 계열 아무거나 하나" 를 표현할 수 없다.

- 큐 · 그래프 → 탐색 계열 보유 시에만 등장
- 스택 → 조건 없음

⚠️ `AugmentCategory` 에 `None` 을 **맨 앞에 넣으면 안 된다.**
enum 값이 밀려 기존 에셋의 분류가 전부 한 칸씩 어긋난다. 맨 뒤에 붙이거나
`AugmentData[] requiresAny` 형태로 간다.

## 미정

- STACK 대기시간 값 / 폭발 간격
- QUEUE 큐 크기 초기값 / 디큐 간격 / 대기 증가율 · 상한
- 유예를 성장축으로 열지
- 평상시 pop 을 유지할지 (없애면 트리거가 크게 단순해진다)
